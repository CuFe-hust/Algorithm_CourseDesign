# Git协作、推送与交付

## 1. 推送main

本地仓库在course-review-platform目录，main是协作底座分支。尚未设置远程仓库；没有自动向任何GitHub账户发布代码。

在GitHub建立目标空仓库后，在本工程目录执行：

```powershell
git status
git branch --show-current
git remote add origin <实际仓库地址>
git push -u origin main
```

如果已有origin先用git remote -v检查，不重复添加或擅自换到其他仓库。目标仓库已有历史时先查看分支与差异，不使用force覆盖。仓库公开/私有由团队决定，真实学生信息及实际测试答案管理需与用途相符。

只推送本工程，不在上级课程文件夹执行git add。main包含示例教师参考答案用于开发，不能把公开开发题库直接当成正式考试的保密测试集。

## 2. 建三个Issue

推送后GitHub New issue可使用三个预置模板；或复制docs/issues的正文新建。指定负责人，替换真实Issue编号。模板未填写任何实际GitHub用户名，当前只是文件，不是已创建的线上Issue。

| Issue | Owner | 先做 |
|---|---|---|
| 教师 | T：队友 | T00共用前端，接着导入、题库和作业写入 |
| 学生 | S：队友 | 当前真实读题/提交页面，接着历史、A01后的互评 |
| 分析 | A：你 | 复用底座，先互评契约/数据/基础流程，再聚合/检测/发布 |

docs/issues为正文源文件，修改后在工程根运行 `python scripts/sync_issue_templates.py` 同步三个GitHub模板，避免正文漂移。模板中的仓库文件使用代码路径，复制到Issue后不依赖失效的相对链接。

## 3. 每人自己的功能分支

```powershell
git switch main
git pull --ff-only
git switch -c feat/teacher-import
```

学生可用feat/student-answer，分析可用feat/analysis-review；名字表示一个小功能，不是一个巨大Issue。完成后提交、推分支、向main提PR，关联实际Issue编号。需要继续任务再建下一分支或按团队约定更新。

三个Issue不等于三个巨大PR。每个PR应独立可运行、可验证，描述当前触发条件、改后的行为、数据库/API影响和验证方式。除明确完成整个Issue外不要在第一个PR误写Closes关闭全部大任务，可先用Refs关联。

## 4. 共享文件与变更顺序

| 内容 | 协调人 | 变更要求 |
|---|---|---|
| db/models、migrations、状态/单位/共享DTO | A | 先说明规则、给输入输出样例，与消费者确认再合并 |
| 前端公共布局/路由/请求/登录 | T00牵头，T/S/A共用 | 首个小PR尽快合并，各功能只注册自己的路由 |
| teacher、student、analysis模块私有实现 | 各模块Owner | 复用公共能力，不直接复制公共模型 |
| 数据字典/API/Issue模板/fixture | 受影响Owner共同维护 | 代码变更同时更新文档和样例 |

数据库变更：拉最新main → 新增迁移 → 在独立验证库从空升级并验证 → 更新模型/数据字典/接口样例 → 消费者适配。禁止改写已应用pg0001及后续迁移。若两个PR同时新增迁移，由A检查顺序与依赖，不让三条互不兼容迁移链并存。

## 5. 每次交接的证据

- 自己电脑按README启动，记下实际Python/PostgreSQL版本和迁移head。
- 涉及业务逻辑的变更提供成功和失败验证；涉及接口给JSON例子；涉及数据库给迁移与回滚限制。
- 真实PostgreSQL公共测试通过；接口变更重新跑HTTP链路。只变文档或低影响配置不堆无意义单测，但检查链接、示例和实际实现一致。
- 不上传.env、实际密码/token、真实学生名册、数据库目录、虚拟环境和日志；仓库已有忽略规则，仍需提交前检查。

## 6. 开发与最终验收

开发期间允许mock，但必须is_mock、确定性输入/输出与可复现落库；业务权限、截止、版本和事务保持真实。最终课程验收需要真实编译测试和核心算法设计/复杂度/实验，不能用模拟值替代。

三个人各交自己模块的完整材料，汇编者只整合格式/索引，不替其他人补实验或代写全部报告。复杂算法研究在流程稳定后共同认领，依据实验选择方案，不预先宣称改进必胜。
