## 2. 执行约定

1. 在现有分支继续，不切换、重置或覆盖工作区中用户已整理和暂存的文档迁移。
2. 新接口先完成最小后端契约及测试，再接前端；已有读题／提交能力直接复用，避免重复搭建。
3. 数据仍使用现有 PostgreSQL／SQLAlchemy／Alembic。认证和评测两组增量顺序迁移，编号按实施时最新 head 生成，不改写 `pg0001`。
4. 文件落点中不存在的路径是**计划新增**，不是当前已有实现；具体文件可依项目结构微调，职责和验收不能省略。
5. 重要权限、事务、并发和恢复场景用有意义的测试验证；简单文案、可逆样式不单独堆镜像实现的测试。
6. 每项提交可审阅变更、对应验证结果和剩余依赖；未完成的教师联调明确记为待交接，不用夹具冒充教师功能完成。
7. 正式开放前必须通过 RV01、RV02、RV03 的竞争／接收保护验收。LOCAL 开发完成不代表已经具备正式 Linux 沙箱隔离。
8. 当前文件是计划基线。实施进展、环境差异和调整在末尾追加；不改写历史执行结果。新增任务继续编号，不重用既有编号。

### SP03 — 认证后端：登录、首次改密、会话和续期

**前置：** SP02。

**文件落点：** `backend/app/common/{auth,security,permissions}.py`，可拆共享账户服务；计划新增 `backend/tests/test_auth_sessions.py`。

- 首次改密前限制业务访问；空闲 2 小时、原认证起点 24 小时上限、普通轮询不续期。

**完成条件／验证：** AC03–AC07、AC27；用可控时钟验证期限，用真实独立数据库连接验证登录／改密／重置交错，不能只用串行调用模拟竞争。覆盖 RV02。

### SP04 — API 接收保护基础

**前置：** SP02–SP03。

**文件落点：** `backend/app/main.py`、`core/{config,errors}.py`、共享限流模块、学生提交服务；计划新增接收保护测试。

- 先实现登录限流及路由专属请求体上限，包含流式、缺少长度或伪造长度的请求；不破坏教师上传上限。
- 实现按稳定账号计数的提交限频、个人／全局积压检查及接收容量锁；已有幂等回执不再次消耗业务额度。
- 返回 413／429／503 和 Retry-After 等结构化反馈，CORS 暴露相应响应头；配置缺失不能视作无限容量。
- 限流计数跨 API 进程原子生效，记录水位及告警接口，具体调度熔断在 SP21 接入。

**完成条件／验证：** AC13、AC28 的接收部分；多进程／连接竞争不突破配额，不因换 token 或请求标识重置额度，失败不留下半份提交。覆盖 RV03 的前置保护。

### SP05 — 共享请求客户端及认证代次

**前置：** SP03–SP04。

**文件落点：** `frontend/src/shared/{api,session}.ts`、`api.test.ts`，必要的会话状态测试。

- 每个请求捕获认证代次及 token 快照；登录、换密和退出推进代次。
- 旧 401 不清新 token；旧续期、旧登录和旧业务响应不能覆盖新身份／期限，续期 Promise 按代次隔离。
- 处理首次改密 403、容量 429、请求过大及配置错误；网络错误保留提交状态，不能误当账号过期。

**完成条件／验证：** AC31、AC25 的共享客户端部分；用可控 Promise 人为反转响应顺序，验证改密／重登录后旧响应安全丢弃。覆盖 RV06。
