### 0.2 相似检测的算法与代价

**算法。** 词法规格化 + Winnowing 指纹（Schleimer、Wilkerson、Aiken，SIGMOD 2003；MOSS 采用的方法）：

1. 词法切分。Python 用标准库 `tokenize`；注释、空行、缩进全部丢弃；标识符统一成 `ID`，数字统一成 `NUM`，字符串统一成 `STR`；关键字与 Python 内置名保留原文（`similarity.py` 的 `tokenize_python`）。
2. k-gram 滚动哈希。取连续 `k = 12` 个记号，Rabin-Karp 滚动哈希，每前进一个记号 O(1) 更新（`_kgram_hashes`）。
3. Winnowing。每 `w = 4` 个连续哈希取最小值（同值取最右），保留下来作为指纹（`winnow`）。
4. 倒排索引计数。按指纹聚合共享数，避免集合两两求交（`compare` 里的 `index` 与 `shared_counts`）。
5. 相似度取双向包含度的较大值 `max(|F_A∩F_B|/|F_A|, |F_A∩F_B|/|F_B|)`，同时输出 Jaccard。

**为什么是它。** 课程场景要防的是"改名、改注释、改缩进、调换语句顺序"这类低成本伪装。词法规格化把标识符和字面量抹平，这三类改写在记号序列上完全不产生差异（第 1 节实测相似度恒为 1.000000），代价只是 O(L)。为什么不直接比 AST：AST 会被"等价写法"和语句拆分完全打散，而指纹能容忍局部插入删除；为什么不两两比集合：O(K²·F) 的常数太大，倒排索引把"只统计被共享的指纹"变成实际工作量。

**复杂度。** 设单个提交记号数 L、指纹数 F（F ≤ L）：

| 步骤 | 时间 | 空间 |
|---|---|---|
| `tokenize_source` | O(L) | O(L) |
| `_kgram_hashes` + `winnow` | O(L) | O(L) |
| 倒排索引构建 | O(ΣF) | O(ΣF) |
| 桶内两两计数 | O(Σ_v C(b_v, 2))，b_v 是共享指纹 v 的归属提交数 | O(命中对数) |
| 证据片段合并 | O(命中数 log 命中数) | O(命中数) |

最后一行的二次项是这套做法唯一会爆炸的地方：K 份高度相似的提交会让所有指纹落进同一个桶，产生 (K²) 量级的桶内配对；证据片段另有 `MAX_PAIRS = 500` 的上限截断。第 6 节的规模实验测的正是这一项，实测结果是 K 从 20 涨到 200（10 倍）时中位耗时从 0.0222 秒涨到 1.4738 秒（66.4 倍），四点双对数斜率 1.8337——接近二次，比 `K²` 的 100 倍略低，因为桶内实际对数少于 `C(K,2)`。

## 1. 相似检测实验一：改名 + 改注释 + 改缩进

**目的。** 验证词法规格化确实把表面改写抹平：同一份代码做过三类伪装后，指纹集合应当一字不差，相似度应为 1.0。

**方法。** 对 70 道题的每一份参考解做 `cosmetic_rewrite`：

1. 一致地重命名所有局部标识符（`local_0`、`local_1`…），但跳过关键字、内置名、`import` 引入的模块名、点号后面的属性名、以及任何作为关键字实参出现的名字（重命名 `sorted(x, key=...)` 里的 `key` 会调用错库函数，这不是"改名"而是改语义）；
2. 把每一行注释原地换成 `# 换过的注释`；
3. 缩进宽度从 4 空格改成 2 空格；
4. 文件末尾追加一行注释。

然后用 `similarity.compare` 比较原始与改写的两份代码（`threshold=0.0`，读回原始相似度）。再对每份改写跑题目自带的测试用例，与原始解的输出逐条比对，确认这确实是"等价改写"而不是"改坏的代码"。

**参数。** k = 12，window = 4，minimum_tokens = 40，threshold = 0.5。

**结果（70 道题全量）。**

| 指标 | 数值 |
|---|---|
| 参与程序 | 70 |
| 改写失败（无法编译） | 0 |
| 记号序列与原始完全一致 | 70 / 70 |
| 相似度 = 1.000000 | 70 / 70 |
| 相似度 min / median / mean / max | 1.000000 / 1.000000 / 1.000000 / 1.000000 |
| 低于阈值 0.5 的程序 | 0 |
| 语义验证通过（对照原解答的 stdout） | 70 程序 / 210 条用例，全部通过 |

表的读法：改名、改注释、改缩进三条加起来，在 70 份形态各异的 Python 参考解上没有产生一个字节的指纹差异。

**结论。** 词法规格化对纯表面改写的免疫是结构性成立的，不是调参调出来的：这三类改写都不改变记号序列，而指纹只由记号序列决定。所以这一组的结果不依赖机器、不依赖 seed，任何一次运行都应当是 70/70，实测也确实是。

**失效场景。** 这一组只说明"抹平"有效，不说明检测有效。它能被这样绕过：在字符串字面量里放语义无关但影响 `STR` token 数量的内容不会起作用（`STR` 被统一），但如果学生把代码改写成完全不同的记号序列（例如把循环改写成递归），这一组就管不到了，见第 2、3 节。

## 2. 相似检测实验二：结构改写（等价写法，不增删语句）

**目的。** 任务判据要求"结构改写后相似度仍高于 0.5 阈值"。这一组测的是只改写法、不改语句数量的结构改写。

**方法。** 用 `ast.NodeTransformer` 做两种机械改写，然后 `ast.unparse` 打印回源码：

1. `x += y` 改成 `x = x + y`；
2. 单比较运算且两侧无副作用（不含调用、下标、海象运算符）时，把 `a < b` 翻成 `b > a`。

这么改的理由：这两类都是"学生被要求把代码改一改"时最常做的动作，而且保持语法树等价。改完照样跑测试用例验证语义。

| [0.4, 0.5) | 3 |
| [0, 0.4) | 4 |

掉到阈值以下的 7 份（这道题、相似度、改写前后记号数）：

| 题目 | 相似度 | 记号数 | 共享指纹 / 原指纹 |
|---|---:|---|---:|
| CODE-P54 树状数组 | 0.320000 | 271 → 316 | 32 / 100 |

### 2.1 这个数字里混进了一个不该有的成分

上面这组改写是"改写法 **+ `ast.unparse` 重新排版**"两件事一起做，所以它测出来的相似度损失不能全部算在那两条语义改写头上。为弄清各占多少，另做了一次诊断（**这次诊断不在交付的 JSON 里**，脚本见本节末尾的说明）：

| 处理方式 | min | median | mean | 低于 0.5 |
|---|---:|---:|---:|---:|
| 只做 `ast.unparse` 重新排版，不做任何改写 | 0.410256 | 0.869219 | 0.865964 | 1 / 70 |
| 只做 `+=` → `= x +`，保持原文排版 | 0.540000 | 0.903361 | 0.893265 | 0 / 70 |
| 第 2 节交付的写法（重新排版 + 两条改写） | 0.320000 | 0.742009 | 0.721438 | 7 / 70 |

**重新排版本身把中位数从 1.000000 压到 0.869219。** 原因是 `ast.unparse` 会改写表达式的写法，与那两条语义改写无关：

- 元组被加上括号：`return a, 1, 0` → `return (a, 1, 0)`，`n, k = data[0], data[1]` → `n, k = (data[0], data[1])`；
- 括号内部的结合方式被重排：`x1 - (a // b) * y1` → `x1 - a // b * y1`；
- 装饰性内容被统一：`if __name__ == "__main__":` → `if __name__ == '__main__':`（整份文件里 `STR` 与 `ID` 的边界因此变化），注释与空行被删掉。

统计上：70 份文件里 **45 份**的括号记号数发生变化，净多出 **128 个括号记号**。12 记号的 k-gram 覆盖不了这么广的改动，所以整份重新排版本身就足以让相似度明显下降。只做语义改写、保持原文排版时，70 份里 **0 份** 掉到阈值以下，中位数 0.903361。

**7 份失败逐份拆开看：**

| 题目 | 只重新排版 | 交付的写法（排版 + 语义改写） | 这道题实际改了几处 |
|---|---:|---:|---|
| CODE-P58 | 0.410256 | 0.410256 | `+=` 0 处、比较 0 处（改写器在这份代码上没找到可改的，输出与只重新排版完全一致） |
| CODE-P54 | 0.740000 | 0.320000 | `+=` 12 处、比较 4 处 |
| CODE-P60 | 0.745763 | 0.389831 | `+=` 4 处、比较 5 处 |
| CODE-P48 | 0.589744 | 0.384615 | `+=` 5 处、比较 6 处 |
| CODE-P12 | 0.644444 | 0.333333 | `+=` 1 处、比较 3 处 |
| CODE-P66 | 0.640000 | 0.400000 | `+=` 3 处、比较 2 处 |
| CODE-P61 | 0.805556 | 0.472222 | `+=` 1 处、比较 1 处 |

**所以第 2 节真实的结论要分成两半。** 一方面，那两条语义改写**确实**有代价：6 份真正被改过的程序，分数都比"只重新排版"时又掉了一大截（CODE-P54 从 0.740000 掉到 0.320000，CODE-P61 从 0.805556 掉到 0.472222）。另一方面，**只做语义改写、保持原文排版时，70 份里 0 份掉到阈值以下**（中位数 0.903361，最低 0.540000）；唯一在"只重新排版"下就已经低于阈值的是 CODE-P58，而那一份的改写器一处都没改到，它的 0.410256 全部来自 `ast.unparse` 的排版差异。

结论因此是：判据"结构改写后仍高于 0.5"成立，但成立得比交付数字看上去更宽裕——**人工改写法、保留原排版时 70/70 通过；交付数字里的 7 份失败是"重新排版 + 密集改写"叠加的结果。**

**失效场景。** 任何"语句级改写 + 程序很短"的组合。另外，凡是先用工具重新格式化再用工具改代码的流程，测出来的相似度都会偏低，评估检测能力时要先把排版因素剔掉。

**关于这次诊断的可复现性。** 诊断脚本没有并进 `backend/scripts/experiment_similarity_complexity.py`，因为它需要一种"按原文本位置做修改"的改写器，与交付脚本里基于 `ast.unparse` 的实现是两套代码。这组数字（0.869219 / 0.903361 / 128 个括号）因此**不在交付 JSON 里**；同类情况还有 4.2 节的误报簇成员名单。两处都在第 9 节与第 10 节末尾汇总。除此之外所有表格都只引用 JSON。

## 3. 相似检测实验三：结构改写（语句拆分 + 插入冗余语句）

**目的。** 测更大的改写力度：把嵌套调用拆成临时变量、在每个循环体开头插入一条冗余赋值。这是刻意规避检测的典型手法。

**方法。** 在第 2 节两种改写的基础上再加两条：

1. `x = f(g(...))` 里若实参是调用或下标，先赋值给临时变量 `_rewritten_N`，再调用；
2. 每个 `for`/`while` 的循环体开头插入 `_rewritten_pad = 0`。

**结果（70 道题全量）。**

| 相似度区间 | 程序数 |
|---|---:|
| [0.8, 1.0) | 3 |
| [0.6, 0.8) | 15 |
| [0.5, 0.6) | 24 |
| [0.4, 0.5) | 14 |
| [0, 0.4) | 14 |

| 指标 | 数值 |
|---|---|
| 相似度 min / median / mean / max | 0.177778 / 0.538462 / 0.522214 / 0.918367 |
| 达到阈值 0.5 | 42 / 70 |
| 低于阈值 0.5 | 28 / 70 |
| 记号数增长比 min / median / max | 1.022 / 1.082 / 1.232 |
| 语义验证通过 | 70 程序 / 210 条用例 |

掉得最狠的 6 份：

| 题目 | 相似度 | 记号数 |
|---|---:|---|
| CODE-P12 切绳子 | 0.177778 | 120 → 135 |
| CODE-P54 树状数组 | 0.210000 | 271 → 334 |

| CODE-P48 第 k 小元素 | 0.282051 | 238 → 269 |

仍有 3 份几乎没受影响（CODE-P53 0.918367，CODE-P14 0.829787，CODE-P17 0.800000），因为它们的分支/循环少、被插入的语句也少。

**结论。** 中位数 0.538462，距离阈值 0.5 只差 0.038；70 道题里 28 道掉到阈值以下。**这一组是本次实验最不理想的相似检测结果**，必须如实记下来：它说明 12 记号的 k-gram 挡得住局部改写，挡不住"每隔几行插一条废话"。插入语句的破坏力与插入条数成正比，与程序大小关系较弱，可以用第 5 节的定量实验看清。

### 3.1 把排版因素剔掉之后

和第 2.1 节同样的担心：这一组也是"语义改写 + `ast.unparse` 重新排版"一起做。以**重新排版后的同一份代码**作为基线再比一次，就能把排版因素剔掉：

| 比较对象 | min | median | mean | 低于 0.5 |
|---|---:|---:|---:|---:|
| 原始 ↔ 只重新排版（第 2.1 节的基线） | 0.410256 | 0.869219 | 0.865964 | 1 / 70 |
| 原始 ↔ 轻改写（第 2 节） | 0.320000 | 0.742009 | 0.721438 | 7 / 70 |
| 原始 ↔ 重改写（第 3 节） | 0.177778 | **0.538462** | 0.522214 | **28 / 70** |
| **重新排版 ↔ 重改写**（剔掉排版后的净效果） | 0.346535 | **0.603913** | 0.620549 | **12 / 70** |
| 重新排版 ↔ 轻改写（剔掉排版后的净效果） | 0.475248 | 0.843274 | 0.835735 | 1 / 70 |

**这组对照修正了结论的措辞：** 重改写本身（语句拆分 + 每个循环体插一条赋值）让中位数从重新排版基线的 0.869219 降到 0.603913，12 份掉到阈值以下；而交付表里的 0.538462 与 28 份是**又叠加了一层整份文件重新排版**的结果。换句话说，"插入冗余语句"确实是导致相似度大幅下降的主因（中位损失 0.265），但**把 28/70 直接读成"算法在真实场景的漏检率"会高估**——真实的改写者不会顺便把整份文件的括号全部重排。**交付 JSON 里的 28/70 是"重排版 + 密集插入"叠加的上界，剔掉排版后的 12/70 更接近只做插入的真实情况。**

**失效场景。** 短程序 + 多处插入；以及循环、分支密集的程序（每个循环体都插一条，等于在全文均匀撒点）。这一组的所有改写都保证语义不变且能通过测试，所以它测出的漏洞是真实的、可被利用的。

**数据来源。** 表里的 `重排版` 基线行与最后两行的净效果都来自 2.1 节说明的那次诊断，**不在 JSON 里**；`原始 ↔ 轻改写` 与 `原始 ↔ 重改写` 两行取自交付 JSON。

## 4. 相似检测实验四：无关实现

**目的。** 判据要求"无关实现应为 0 对，或低于阈值"。这里分两个层次测：同一道题的不同算法（真误报），和 70 道不同题目的两两比较（误报底噪）。

### 4.1 同一道题的两套正确算法

**方法。** 手写 5 份与参考解算法不同的实现，逐份跑该题全部测试用例确认正确，再与参考解比相似度。

**结果。**

| 题目 | 另一套算法 | 参考解记号数 | 另一套记号数 | 用例 | 正确 | 相似度 | 共享指纹 |
|---|---|---|---:|---:|---:|---|---:|---:|
| CODE-P01 活动安排 | 区间 DP 求最长不重叠活动链 | 126 | 158 | 5 | 是 | 0.688889 | 31 |
| CODE-P10 逆序对 | 双重循环直接数逆序对 | 234 | 95 | 5 | 是 | 0.000000 | 0 |
| CODE-P18 最长上升子序列 | O(n²) 动态规划 | 110 | 116 | 5 | 是 | 0.000000 | 0 |
| CODE-P49 二分查找 | 每次询问线性扫描 | 160 | 132 | 5 | 是 | 0.640000 | 32 |
| CODE-P63 只出现一次的数 | 排序后相邻比较 | 71 | 96 | 5 | 是 | 0.041667 | 1 |

min / median / mean / max = 0.000000 / 0.041667 / 0.274111 / 0.688889；**2/5 达到阈值 0.5**。

**结论。** 两个误报都是"同一道题的两种正确写法共享大量脚手架"：CODE-P01 的两份实现都要读入、都要 `acts.sort()`、都要遍历一遍计数，这些行本来就该被认成相似；CODE-P49 的两份实现都要读同样的输入、同样逐条回答询问、同样拼输出。**在这些位置上高相似度并非算法错误，而是"结构相同"这个事实本身。** 但它确实说明：阈值 0.5 在这类题上会给出教师需要人工排除的线索。

**失效场景。** 框架代码多、核心算法只占少数的题目（输入解析、排序、输出格式化占了大部分记号）。同一份作业里学生都用同一套模板开头时，误报会集中出现。

### 4.2 70 道不同题目的参考解两两比较

**结果。**

`compare` 还会把这些误报连成簇，簇比对数更能说明底噪的形状：

| 簇 | 成员 | 大小 | 簇内最大相似度 |
|---|---|---:|---:|
| 1 | CODE-P04、CODE-P07、CODE-P08、CODE-P22、CODE-P23、CODE-P25、CODE-P51、CODE-P52 | 8 | 0.671053 |
| 2 | CODE-P16、CODE-P29、CODE-P54、CODE-P70 | 4 | 0.517857 |

8 人簇的核心是 CODE-P25（只有 29 个指纹的短程序）——它与另外 7 个题目各有一对过阈值的配对，其中 5 对是"17 个共享指纹 / 29 个自身指纹 = 0.586207"。**这正是包含度作为相似度量的固有弱点：分母小到二三十个指纹时，撞上十几段公共脚手架就够过阈值。** 该弱点在真实使用中不会跨题发作（`baseline.py` 限定单题范围），但同一道题内所有学生都写短程序时，它依然会抬高误报。

**这张簇表的来源。** 交付 JSON 对 4.2 节只记录了 `compare_pair_count = 18` 与 `compare_cluster_count = 2`，没有记录簇成员。成员名单是用同一份参考解、同一组参数复跑一次 `compare` 得到的（输入和参数都在 JSON 里，可复现）。这是本文两处"数字不在 JSON 里"之一，第 9 节与第 10 节末尾都记了。

**失效场景。** 该实验的 18 对全部是"短程序 + 同族算法"，说明阈值 0.5 在指纹数少于约 55 时会系统性地偏松。实际使用中不跨题比较（`baseline.py` 里 `code_similarity` 对跨题输入直接 `raise ValueError`），所以这 18 对不会真的出现在教师页面上；它们的作用是给出这套度量的底噪，供解释"为什么需要人工复核"。

### 4.3 独立完成基线：阈值到底校准了什么

**目的。** 前面三节比较的都是"参考解 vs 改写过的副本"与"参考解 vs 另一种算法"。教师真正面对的问题没被回答：**同一道题、两个学生各自独立做题、没有复制关系，相似度会是多少？** 这个基线决定 0.5 这个阈值有没有校准意义。

**方法。** 三组对照，全部是独立写作、无语义等价改写、无复制：

1. 短题目（活动安排贪心）、I/O 习惯各异（`sys.stdin.read`、`input()`、`sys.stdin.readline` 三种）；
2. 短题目、**统一 I/O 惯用法**（三份都用 `sys.stdin.read().split()`，模拟被同一门课教出来的班级）；
3. 长题目（石子合并区间 DP），同一算法的两份独立实现。

**结果。**

| 组 | 程序记号数 | 三对相似度 | 达到或超过 0.5 的对数 |
|---|---|---|---:|
| 短题目 · I/O 习惯各异 | 82–126 | 0.354839 / 0.193548 / 0.031250 | 0 / 3 |
| 短题目 · 统一 I/O 惯用法 | 109 | **1.000000** / **0.583333** / **0.583333** | **3 / 3** |
| 长题目 · 独立实现 | 202–219 | 0.311688 | 0 / 1 |

**结论。** 阈值 0.5 的含义完全取决于语境：

- 学生各自形成不同的写法时，独立完成的相似度在 0.03–0.35，**远低于阈值**，此时"超过阈值"确实有信号价值；
- 一旦全班被教了同一种 I/O 惯用法，**独立完成的三对全部达到或超过阈值，其中一对是 1.000000**——两个没有复制关系的学生，指纹完全一致；
- 长程序（200 记号以上、算法有自由度）即使同一算法，独立实现也只有 0.31。

也就是说：**相似度的证据强度与程序长度强相关，而产品此前完全没有呈现这一点。** 短题目（约 120 记号以下）的高相似度不能作为抄袭线索；教师看到的"1.000000"可能只是两个诚实学生的必然重合。

**据此做的产品改动**（不在本实验脚本里，在教师端与学生端）：

1. 配对表新增双方记号数；
2. 任一侧少于 120 记号时标注"程序较短，独立完成也可能达到此相似度"；
3. 相似度落在 [0.5, 0.7) 时标注"该区间内同题的不同正确算法也可能出现"（依据第 4.1 节的 0.688889）；
4. 相似簇展示"达标 X/Y 对"与簇内最低相似度，并给链式归组打"链式"标记（依据第 4.4 节）。

**失效场景。** 本组只有三份短程序与两份长程序，样本小；"统一惯用法"是我按课堂常见形态构造的，真实班级的惯用法一致性可能更强（老师给了模板）也可能更弱。它证明的是方向与量级，不是精确的分界线。

### 4.4 相似簇不是团：链式归组的实测

**目的。** 簇由阈值图上的并查集（单链）算出，因此是连通分量而不是完全图。教师看到"3 份相似簇"的直觉是三人互相抄，实际可能是一条链。

**方法。** 构造 A 含块 1、B 含块 1+块 2、C 含块 2 的三份提交：A~B 与 B~C 达标，A~C 只共享读入模板、不达标。

**结果。** 簇成员 3 人，达标配对 2 对（总组合 3 对），最高 1.000000、最低 0.857143。若只展示"3 份 · 最高 1.000000"，链式结构完全不可见。

**结论。** 簇的呈现必须带上"达标 X/Y"，否则会把链包装成团。

## 5. 相似检测实验五：插入语句的边际代价

**目的。** 第 3 节显示插入冗余语句能把中位数压到 0.538，但没说明"压多少"。这一组固定同一份代码，只改变插入条数。

**方法。** 取 CODE-P26（单源最短路，235 个记号、92 个指纹），在"下一条语句缩进不更深、且当前行不以冒号结尾"的安全位置均匀插入 `inserted_i = i` 形式的冗余赋值，条数分别取 1、2、3、4、8。

**结果。**

| 插入条数 | 记号数 | 唯一指纹数 | 共享指纹 | 相似度 | 最长连续记号 |
|---:|---:|---:|---:|---:|---:|
| 1 | 235 → 238 | 92 → 94 | 92 | 1.000000 | 103 |
| 2 | 235 → 241 | 92 → 95 | 88 | 0.956522 | 59 |
| 3 | 235 → 244 | 92 → 94 | 82 | 0.891304 | 44 |
| 4 | 235 → 247 | 92 → 96 | 79 | 0.858696 | 33 |
| 8 | 235 → 259 | 92 → 97 | 61 | 0.663043 | 37 |

**结论。** 插入 1 条几乎不掉（1.000000），因为 12 记号的 k-gram 只被破坏一次，winnowing 窗口里还有其他指纹兜底；从 2 条起开始掉；8 条时掉到 0.663043。**这一组是干净测量：它直接在原文本里插入语句，没有经过 `ast.unparse`，所以掉下去的分数全部归因于插入本身**（第 2.1、3.1 节证明重新排版另有 0.130781 的中位损失，这里没有那个成分）。它给出的是"插入"这一种手法的单独代价曲线：8 条插入 = 0.663043，仍高于阈值；而第 3 节的重改写是"每个循环体都插一条"，插入条数远多于 8，所以才会跌到中位数 0.538462。

**失效场景。** 本组只测了一份代码和一种插入方式（每处一条赋值）。若插入内容更长（例如多行注释块被转成语句），破坏会更早出现；若插入位置更密集（每个循环体），破坏会更大——第 3 节就是那个方向。

## 6. 相似检测实验六：随提交数 K 的增长

**目的。** 验证 `compare()` 的实际耗时与指纹规模随提交数增长的趋势，确认倒排索引实现在 200 人量级可用，并暴露证据列表的截断行为。

**方法。** 以 CODE-P26 为母本（235 个记号、92 个指纹），复制 K 份，每份随机挑一个"本题自己绑定的标识符"做一次一致重命名，再追加一行注释（随机源固定为 `SEED`，所以每份改动可复现）。K = 20/50/100/200，每次 `compare` 跑 3 遍取中位数。

**结果。**

| K | 耗时中位数(s) | min–max(s) | 唯一指纹总数 | 候选对数 | 输出对数 | 触发 500 对上限 | 簇数 | 簇大小 |
|---:|---:|---|---:|---:|---:|---|---:|---|
| 20 | 0.0222 | 0.0221–0.0223 | 1840 | 190 | 190 | 否 | 1 | 20 |
| 50 | 0.0999 | 0.0955–0.1091 | 4600 | 1225 | 500 | 是 | 1 | 50 |
| 100 | 0.3998 | 0.3768–0.4049 | 9200 | 4950 | 500 | 是 | 1 | 100 |
| 200 | 1.4738 | 1.4664–1.5629 | 18400 | 19900 | 500 | 是 | 1 | 200 |

翻倍倍数：4.500 / 4.002 / 3.686；四点的双对数斜率 **1.8337**。

**结论。** 200 人 **1.47 秒**、100 人 **0.40 秒**、50 人 **0.10 秒**，单题批次在秒级完成，符合“200 人量级可用”的设计预期。四点双对数斜率 **1.8337**，接近 K²（桶内两两计数是二次项），远快于线性；翻倍倍数 4.500 / 4.002 / 3.686 波动较大（100 人那档的 min–max 是 0.3768–0.4049，明显受机器负载影响），所以只报中位数与总斜率。

**一个必须写清楚的现象：** K ≥ 50 时输出对数被 `MAX_PAIRS = 500` 截断（候选 1225/4950/19900，输出都是 500）。截断只影响证据列表，不影响簇：四组都是 1 个簇、成员数等于 K（20/50/100/200），因为 `compare` 用完整的阈值图上做并查集算簇，与截断后的 `pairs` 无关。也就是说规模实验里 200 份提交仍然被正确识别成一个 200 人的相似簇，但 500 对上限意味着教师一次只能看到 500 条证据。

这个"被截断了"的事实现在是可见的：`similarity.py` 的 `ItemResult.pairs_truncated` 字段、`baseline.py` 的返回字典、`similarity_service.py` 的教师投影和前端 `Similarity.vue` 的提示条都带上了它。**这个字段在本次实验之前是丢的**——`compare` 用 `result.pairs_truncated = True` 挂在 dataclass 上，但 `baseline.py` 重组返回字典时没有把它带出来，教师页看到 500 条证据也不会知道自己看到的只是前 500 条。这一条是本次实验（K=50/100/200 三行的"触发 500 对上限 = 是"）顺带暴露并修好的，对应第 8.5 节。

**失效场景。** 本组每份提交只改动一个标识符，所以彼此相似度 1.0、全部进同一个桶，这是最坏情况下的桶长度（真实作业里相似度分布分散，桶会小很多）。相对地，真实场景里若一份作业有 200 人且大范围抄袭，上述 1.40 秒与 500 对上限就都适用。

## 7. 复杂度实验

本节把 6 个参考程序交给 `probe.escalating_measure` 生成输入并真实执行，再用 `complexity.classify_growth` 与 `complexity.combine` 得到最终结论。每个程序只跑一次（第 7.9 节的重复性实验另计），所有数字来自交付的 JSON。

### 7.1 方法

每组的参数、伸缩档族、墙钟上限与预算都记在 JSON 的 `complexity.groups[].parameters` 里。统一设置：单档墙钟上限 4000 ms、总预算 60000 ms、每档重复 5 次取中位数、最多 13 档。实测值取中位数；`reference_ms` 是同一档上纯输入读取程序的耗时；`io_ratio = wall_ms / reference_ms`。

### 7.10 拟合器的噪声敏感性

**目的。** 第 7.9 节只有两组、各 3 次重复，样本太少。这一节把理想曲线加上乘性噪声后每组重复 40 次，直接量化“置信度 HIGH 不等于结论正确”。

**方法。** 取 7 档（256 … 16384），对每个理想类别生成 `t = (12 ms + 24 ms·f(n)/f(256)) × (1 + σ·Z)`，`Z` 是标准正态，σ 取 2% / 5% / 10%。随机源固定（`seed = 20261045`），可复现。

**结果。**

| 理想类别 | σ=2% 命中 | σ=5% 命中 | σ=10% 命中 | σ=10% 报错且置信度 ≥ MEDIUM |
|---|---:|---:|---:|---:|
| `O(1)` | 15/40 | 23/40 | 24/40 | 0/40 |
| `O(log n)` | 40/40 | 40/40 | 40/40 | 0/40 |
| `O(n)` | 40/40 | 30/40 | 28/40 | 12/40 |
| `O(n log n)` | 40/40 | 36/40 | 27/40 | 13/40 |
| `O(n^2)` | 38/40 | 34/40 | 20/40 | 20/40 |
| `O(n^3)` | 40/40 | 40/40 | 40/40 | 0/40 |

**结论。** 三个事实：

1. **无噪声能判对不代表有噪声能判对。** σ=2% 时 `O(n log n)` 40 次全对，σ=5% 掉到 36 次，σ=10% 掉到 27 次；`O(n)` 在 σ=10% 有 12 次被报成 `O(n log n)`。这是“只差一个 log 因子”的直接证据。
2. **置信度不是正确率的保证。** σ=10% 时 `O(n^2)` 有 20 次被报成 `O(n^2 log n)`，其中 20 次的置信度仍在 MEDIUM 以上。
3. **两端更稳。** `O(log n)` 与 `O(n^3)` 在所有噪声水平下都是 40/40 全对，因为它们的基函数与相邻类别差别足够大。

**失效场景。** 噪声超过 10% 时这张表会进一步退化。本机实验期间不空，实测噪声已接近 5–10% 的量级（见第 9 节），所以 σ=5%/10% 两列比 σ=2% 更接近真实部署条件。

## 8. 发现的问题与修复

这一节是本次实验的主要产出：七个缺陷。它们都不是读代码看出来的，而是把**无噪声的理想曲线**、**带噪声的重复**、**真实测量**和**字段传递链**分别喂给怀疑的地方之后，用数字逼出来的。五条都已修复；本报告所有数字都来自修复后的代码与修复后重新生成的 `experiments-2026-10-28.json`（生成于 2026-10-28T10:15:34，整轮 97.4 秒）。

### 8.1 缺陷一：无噪声的 O(n log n) 被判成 O(n)，5 次全错

**怎么发现的。** 标定实验（`fit_calibration`）把 `complexity.py` 自己的 `GROWTH_FUNCTIONS` 拿来构造理想曲线 `t = 12 ms + c·f(n)`，完全没有测量噪声，再喂给 `fit_growth`。在 5 种梯子跨度（4 倍、8 倍、16 倍、64 倍、256 倍）、每类 7 档的设置下，按旧规则的运行有 30 组里 5 组判错，且全部是同一个方向：`O(n log n)` 的 5 次全部被报成 `O(n)`，置信度还是 HIGH。

**数字。** 各跨度下 `O(n log n)` 与 `O(n)` 的 R² 差：

| 梯子跨度 | `O(n log n)` R² | `O(n)` R² | 差值 |
|---|---:|---:|---:|
| 4 倍 | 1.000000 | 0.999360 | 0.000640 |
| 8 倍 | 1.000000 | 0.998757 | 0.001243 |
| 16 倍 | 1.000000 | 0.997482 | 0.002518 |
| 64 倍 | 1.000000 | 0.997060 | 0.002940 |
| 256 倍 | 1.000000 | 0.997870 | 0.002130 |

五次差值都小于旧规则的并列门槛 0.005，而旧规则“并列时取更低阶”因此每次都选 `O(n)`。这不是“差一点点”，是**在倍增梯子上 `n` 与 `n log n` 几乎共线，R² 这个指标本身不携带区分信息**。

**根本原因。** 拟合 `t = a·f(n) + b` 时，`f(n) = n` 与 `f(n) = n log n` 在 `n ∈ [256, 65536]` 上的相关系数高于 0.999，两个基函数几乎线性相关，最小二乘残差只差千分之一量级。用“R² 差小于 0.005 就取低阶”这种规则，等于在任何梯子上都强制把 `n log n` 压成 `n`。

**修复。** 按残差平方和（SSE）选类，并给降阶设一个门槛：只有当相邻的更低阶候选的残差不超过当前的 `exp(2/m)` 倍时才降一级，`m` 是有效档位数（`_choose_class` 与 `sse_improvement_fold`）。`exp(2/m)` 是经验性的保守折减系数（7 档 1.33、13 档 1.17），不是信息准则推导——八类候选都是两个参数（`a`、`b`），彼此没有参数个数差异。降阶只允许一级一级走，避免一次从 `O(n^2)` 跳到 `O(1)`。

**修复后的效果。** 同一套标定实验 30 组（6 类 × 5 种跨度）**0 组判错**。真实数据的验证见第 7.5 节：实测与结构都给出 `O(n log n)`。

### 8.2 缺陷二：只差一个 log 因子的两类，时钟分辨不了

**怎么发现的。** 第 8.1 节说明“理想曲线也判错”，那只是规则问题。另一条线索来自重复测量：同一份 `O(n log n)` 程序连测，实测类别会在 `O(n log n)` 与 `O(n)` 之间摆动。第 7.10 节把这件事做成了可复现实验：**同一形状的理想曲线按 σ = 5% / 10% 加噪声后各重复 40 次，`O(n log n)` 分别有 4 次和 13 次被报成 `O(n)`，`O(n)` 分别有 10 次和 12 次被报成 `O(n log n)`。**

**原因。** `n` 与 `n log n` 在整个可测区间内相差不到约 1.2 倍，远小于档位间隔与测量噪声。计时在原理上无法区分它们，靠调阈值只能换一个方向的错误。

**修复。** `combine` 增加一条前置规则：`O(1)/O(log n)`、`O(n)/O(n log n)`、`O(n^2)/O(n^2 log n)` 这三对只差一个 log 因子的类别，由结构分析裁定；实测落在另一边时把分歧写进限制说明（`_LOG_FACTOR_PAIRS`、`_log_factor_pair`）。理由：结构分析看得到产生 log 因子的构造（排序调用、循环内折半），时钟看不到。

**修复后的效果。** 第 7.9 节 `Onlog` 组第 2 次实测报 `O(n)` 且置信度 HIGH，最终仍按结构给 `O(n log n)`；第 7.6 节 `On2` 组实测报 `O(n^2 log n)`，最终按结构给 `O(n^2)`。**这不是“现在全对了”：噪声下 log 因子的实测仍然会错，只是不再由不稳定的那一路独断。**

### 8.3 缺陷三：实测至少 5 档才发布，而档位停止条件写在 4 档

**怎么发现的。** 第 7.6 节按旧代码跑出只有 4 档、置信度只能 LOW，结论回落到结构分析。检查发现两处数字各写各的：`probe.escalating_measure` 在 `len(executed) >= 4` 时停止，`fit_growth` 要求 5 档才给 MEDIUM。两者叠加的后果是：**每一道平方及更高阶的程序都永远拿不到 5 档，实测永远只能给 LOW，永远被结构分析覆盖**——最该被测量的那一类程序反而永久失去测量。

**修复。** 抽出常量 `MINIMUM_PUBLISHABLE_RUNGS = 5`，`probe.py` 直接引用它（`MINIMUM_RUNGS_BEFORE_STOPPING = growth_rules.MINIMUM_PUBLISHABLE_RUNGS`），两处不可能再漂移。修复后第 7.6 节拿到 5 档、实测 R² 0.999975、置信度 HIGH。

### 8.4 缺陷四：字面量边界的循环被当成随 n 增长

**怎么发现的。** 第 7.3 节的手写程序是“6 万次固定迭代，每次做一次二分”。旧静态分析把 `for _ in range(60000)` 记成一层多项式循环，整个程序算成 `O(n log n)`；真值是 `O(log n)`。

**修复。** 新增 `_constant_iteration`：`range(<字面量>)` 判定为常数层，`_CostStack.push/pop` 同步支持 `const`，静态分析现在给 `O(log n)`，与实测一致。

**这次修复自己又引出一个缺陷，由独立审核发现。** 第一版只改了 `push` 没改 `pop`：`push('const')` 不加层数，`pop('const')` 却减了一层，于是“外层 n 循环里先出现字面量循环、再出现真正的内层 n 循环”的代码会被抹掉外层代价。审核给出的实例是 `for i in range(n)` 里先 `for b in range(8)` 再 `for j in range(n)`，旧版本报 `O(n)`，真值 `O(n^2)`；题库里 CODE-P37 也受影响。修复是让 `pop` 与 `push` 用同一套判断，`const` 直接返回。现在三种排列顺序都判 `O(n^2)`，并有单测固定。

### 8.5 缺陷五：截断标记写进对象却没传到界面

**怎么发现的。** 第 6 节规模实验里 K ≥ 50 时证据列表被 `MAX_PAIRS = 500` 截断。算法把标记挂在 `ItemResult` 上（`result.pairs_truncated = True`，运行时加属性），但 `baseline.code_similarity` 的返回字典里没有这个键，接口也就拿不到，教师看到的 500 行和“只有 500 对”无法区分。

**修复。** `pairs_truncated` 成为 `ItemResult` 的正式字段，契约 `SimilarityOutput` 增加同名字段，`baseline` 透传，教师端接口返回它，页面在截断时明确写“证据列表已截断：只显示相似度最高的 500 对，相似簇仍按全部配对计算”。

### 8.6 缺陷六："实测只能给上界"的判据从未生效

**怎么发现的。** 方案审核把 `DynamicConclusion` 的注释逐字对照数据：注释说实测类别高于纯读取类别才算有信息，但当时代码先给基线自己拟一条曲线、再比类别。基线是常数开销程序，它自己的拟合几乎必然落在启动底噪上、置信度 LOW，于是 `io_class` 永远是 `UNKNOWN`，`informative` 永远是 `True`——判据空转，实测只要置信度够就直接定案，与文档宣称的语义相反。核对 JSON 六组加自测四组：`io_class` 100% `UNKNOWN`、`reference_fit` 100% 为 `None`。

**修复。** 改成逐档比值判定：完成档里有至少 `MINIMUM_INFORMATIVE_RUNGS = 3` 档的 `wall_ms / reference_ms >= INFORMATIVE_IO_RATIO = 1.5` 才算有信息（`classify_growth`）。没有基线时（参考程序只有 Python，C/C++/Java 没有）不判否，而是在报告里写明"实测未经输入开销校验"。

**修复后的效果。** 这条规则第一次真实生效，并且立刻改变了结论：第 7.4 节的线性组、第 7.2 节的常数组都被判为 `informative = False`（全程没跑赢读输入），实测回落为仅作上界，结论取自结构分析——正是文档一直承诺的行为。

### 8.7 缺陷七：三分之一题目的伸缩档与真实输入格式不匹配

**怎么发现的。** 方案审核把 63 道可测题逐一生成 `n = 256` 的输入喂题库自带的 Python 参考解：42 道正常，21 道直接崩溃。原因不是笔误，是 11 个族的表达力覆盖不了题库的真实格式——首行双参数（背包的 `n W`）、无权图的二元边（`u v`）、三个整数、数字串输入等。

**后果。** 这些题的所有学生提交在每一档都运行错误，报告只能显示失败档位；测量成本全部白烧，而学生看到的是"分析失败"。

**修复。** 两层：一是给族加参数（`edge_arity` 二元/三元边、`header_extra` 首行附加参数），修好 6 道（P03/P16 背包、P29/P31/P32/P33/P34 图中的 5 道按验收结果部分保留）；二是 seed 时用参考解做自动验收——生成输入喂参考解，崩溃就把该题降级为 `EXISTING_CASES`（仅结构分析）并记录原因。验收后 70 道题里 40 道可测、全部通过，31 道明确标为仅结构分析（7 道输出规模过大 + 24 道族不匹配）。

**这不是零成本的完美方案。** 40/70 可测意味着三成题目拿不到实测结论；要再提高只能继续扩充族或换自动推断，而自动推断自然语言题面比枚举族更不可靠。

### 8.8 修复没有让一切变好

必须说清楚四点：

1. **6/6 组一致不等于方法可靠。** 6 组里只有 2 组由实测定案，其余靠结构分析。把实验条件稍作变化（提高单档墙钟上限、换更快的机器），这些结果会变。
2. **log 因子在噪声下仍不稳定。** 第 7.10 节的数字是修复后的结果，σ=10% 时 `O(n log n)` 只有 27/40 命中。修复只是把裁决权交给更稳的那一路。
3. **标定实验的成功是必要条件而非充分条件。** “把理想曲线喂进去都判对”只说明规则内部自洽。
4. **静态分析也会错。** 第 8.4 节的 `pop` 缺陷与字面量循环问题都说明结构这一路同样需要审核与测试，不能因为它是“确定性的”就当作正确。

## 9. 实验的局限

- **墙钟有波动，且本轮实验期间机器不空。** 同一组程序三次重复的耗时会浮动（第 7.9 节的单次明细可查）；各组的最深层结论在这三次里稳定，但 R²、exponent、单档耗时不能当精确值引用。脚本固定了 seed 与档位，所以**结构与指纹数完全可复现，耗时与类别判定只可复现到“大概率相同”**。
- **参考解是 Python 实现。** 70 道题的参考解含多种语言，而本实验只取 Python；`probe.IO_REFERENCE` 也只为 `python3`/`python` 提供纯读取基线。C/C++/Java 的相似检测（词法器）与复杂度分析（`analyze_lexical`，置信度固定 LOW）没有被这套实验覆盖，数字不能直接迁移。Python 的启动底噪（12–25 ms）是本次所有拟合的常数项来源，换成编译型语言后量级完全不同。
- **70 道题不等于真实学生代码分布。** 题库参考解写得整齐、命名规范；真实提交更长、更啰嗦、调试残留更多。这会影响第 4.2 节的误报底噪与第 2、3 节的改写敏感性，也难以给出定量关系。**70 份参考解、2415 个配对、以及改写实验的 70 份样本，不足以支撑关于课堂真实误报率的推断。**
- **改写由脚本机械生成。** 第 2、3、5 节用的是 `ast` 变换的固定套路。真人改写的形态（重排函数、抽公共方法、替换数据结构）没有覆盖，测出的是“这类改写的下界”。
- **只测了算法层，没测服务层。** 存储、批次状态机、教师投影、并发领取都不在实验范围内（第 8.5 节说明这类链路确实出过问题）。
- **单次运行。** 复杂度六组各只跑一次（第 7.9 节除外）；噪声实验是 40 次重复，但它用的是合成曲线，不是真实执行。
- **伸缩档只覆盖 40/70 道题。** 第 8.7 节的自动验收把 24 道族不匹配的题降级为仅结构分析，另有 7 道因输出规模过大不测。三成题目拿不到实测结论，是本方案已接受的覆盖代价。
- **独立完成基线只有三组对照。** 第 4.3 节证明"短题目 + 统一惯用法"下独立完成可以到 1.000000，但样本只有三份短程序与两份长程序；它给的是方向与量级，不是精确的长度分界线（120 记号是保守取值，不是测出来的临界点）。
- **相似检测的规模实验是最坏情况。** 第 6 节每份提交只改一个标识符，彼此相似度 1.0，全部落进同一个桶；真实作业的相似度分布分散得多。
