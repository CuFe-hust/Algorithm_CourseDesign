# 已通过代码的复杂度分析（已实现）

> **已被取代。** 本文描述 2026-10-28 的第一版实现（墙钟计时 + 静态结构分析）。它已被[执行轨迹计数与递推推断](complexity-trace.md)取代，代码与迁移也随之下线；保留本文作为上一版尝试的完整档案。

日期：2026-10-28。实现位于 `backend/app/analysis/algorithms/complexity.py`（纯函数）、`probe.py`（输入生成与测量）、`complexity_service.py`（状态机与投影）、`scripts/run_complexity.py`（worker）与前端 `ComplexityPanel.vue`、`GrowthChart.vue`。拟合规则的依据来自[算法实验](algorithm-experiments.md)，那里的数字是用本实现本人跑出来的。

## 1. 它回答什么

一段**真实通过**的代码，运行时间随输入规模怎么长、空间怎么长。给学生的是一张增长曲线、一个复杂度类别、置信度和逐条结构证据；它不参与评分。

资格条件全部满足才分析：`ACCEPTED`、`is_mock=false`、通过点数等于总数、当前执行环境内、语言受支持。任何一条不满足就返回 409 并说明原因，不编造报告。

## 2. 两个独立估计器

### 2.1 静态结构分析

Python 用标准库 `ast`，C/C++/Java 只用词法与括号结构。

Python 收集的事实：

| 事实 | 用途 |
|---|---|
| 循环嵌套，按（多项式层数, 对数层数）记录 | `while lo<hi: mid=(lo+hi)//2` 记对数层；`for` 记多项式层；`for _ in range(60000)` 与 `[x for _ in range(9)]` 这类字面量边界记 0 层（与输入规模无关） |
| `while` 的边界 | 一律按随输入增长计。`while t < 9` 可能是常数，但语法上看不出 t 是否被输入驱动，而 `while lo < n` 是二分查找的标准写法；宁可高报一阶，也不把真实的 n 循环判成常数 |
| 折半收缩（`//2`、`>>1`、`a[mid:]`） | 分治、二分、快速幂 |
| 递归形态（折半 / 递减 / 常数参数）与递归调用数 | 单路折半 → log n；双路折半 → 分治；双路常数 → 2^n；单路递减含循环 → n² |
| 排序调用 | 引入 log n 因子 |
| 容器分配（推导式、`list(...)`、`[[0]*n]`） | 空间下界；二维表 → O(n²) |
| 递归深度 | 调用栈空间 |

结论是类别 + 证据列表（行号 + 原因）。C/C++/Java 固定 `confidence=LOW`，证据里带 `LEXICAL_ONLY`，报告写明没有语法树。

### 2.2 经验增长测量

平台无法为任意题目自动造数据，因此每题有一份**伸缩档**（`problem_complexity_profiles`）：声明输入形态族与规模上限。11 个族覆盖单整数、两个整数、整数数组、成对行、图边、两串、单串、网格、矩阵、固定输入、不可测量。

测量流程：

1. 编译一次，然后按倍增序列（256、512 … 至多 13 档）逐档运行。
2. 每档跑 3 次取中位数；单档墙钟上限 10 秒，总预算 150 秒。
3. 同一档额外跑一个**纯输入读取程序**（只读、切分、转换、打印），作为该档输入解析成本。
4. 停止条件：最大档超过 250 ms、或倍数已达 8 倍且至少 4 档有效、或超时、或触顶。停止原因写进报告。
5. 每档用 `os.wait4` 取得该子进程自己的 `ru_maxrss`（不是全进程累计最大值），换算为 KiB。

执行复用 `app/judge/local.py` 的启动门、进程组终止与输出上限，不另写执行器；测量在 `scripts/run_complexity.py` 独立进程中做，不占评测队列。

### 2.3 拟合

对每个候选类别 `f(n) ∈ {1, log n, n, n log n, n², n² log n, n³, 2ⁿ}` 拟合 `t = a·f(n) + b`，`a>0`、`b≥0`：

- `b` 必须允许为正：进程启动、解释器预热是每档都有的常数，忽略它会系统性低估增长。
- R² 只用来圈定候选：相差 0.005 以内的类别视为同样贴合。在倍增梯子上 `n` 与 `n log n` 几乎共线，R² 只差约 0.0006，靠 R² 排序必然选错，这一点由[实验](algorithm-experiments.md)实测确认（无噪声的理想 `n log n` 曲线 5 次全部被判成 `O(n)`）。
- 圈定候选后按**残差平方和**选：先取残差最小者，再**一级一级**考虑降阶，只有相邻的下一阶模型残差不超过当前的 `exp(2/m)` 倍时才降一级。`exp(2/m)` 是经验性的保守系数，不是信息准则推导：八类候选都是两个参数（`a` 和 `b`），不存在“多一个参数”的代价，这个系数的作用是让档位越多越敢认高阶。只允许降一级是必要的，否则一次扫描可能在多个粗类别都落进同一个 R² 窗口时从 `O(n²)` 直接跳到 `O(1)`。
- 另算双对数斜率作为物理校验，与类别预期指数相差超过 0.7 的候选被排除。
- 至少 5 个有效档位才给 MEDIUM 及以上置信度。4 档时实验观察到 `O(n²)` 会被判成 `O(n log n)`，档位不足以钉住曲线。

### 2.4 "实测只能给上界"的判据

实测只有在**明显跑赢读输入**时才算证据：完成档里至少 3 档的 `wall_ms / reference_ms ≥ 1.5` 才判 `informative = True`（`INFORMATIVE_IO_RATIO`、`MINIMUM_INFORMATIVE_RUNGS`），否则结论回落到结构分析并写明理由。

这条规则此前写成了"先给基线自己拟一条曲线再比类别"，而基线是常数开销程序、它的拟合几乎必然 LOW，于是判据从未生效（方案审核发现）。改成逐档比值后它第一次真正工作：实验里线性组与常数组都被正确判为可测信息不足。

没有基线时（参考程序只有 Python）不判否：报告写明"实测未经输入开销校验"，因为 C/C++/Java 没有别的可发表结论来源。

### 2.4 合并规则

1. **只差一个 log 因子的两类由结构裁定。** `n` 与 `n log n`（以及 `1`/`log n`、`n²`/`n² log n`）在整个可测区间内相差不到一个常数倍，计时无法分辨：实验里 40 次带噪声的对照有 13 次分错。结构分析能看到产生 log 因子的构造（排序调用、循环内的折半），所以这一类按结构报，同时把实测落在另一边的分歧写进限制说明。两条都是 log 关系时（`O(log n)` 与 `O(n log n)`）不属于同一对，不适用这条。
2. 其余情况，实测类别**高于**纯读取类别（说明程序确实比读输入慢了），且置信度不是 LOW → 时间结论取实测。
3. 否则以结构分析为准。原因写清楚：实测总时间与纯读取同阶，只能给出上界，分不出更便宜的算法（二分查找就是这种情况）。
4. 两者不一致时两条都保留，并写明取舍理由。
5. 空间以结构分析为主；实测内存确实随规模增长且更高时才上调，并注明。实测内存判定用“超出最小档的增量”（总 RSS 里解释器底噪占大头，直接除以 n 会永远测不出线性空间），要求至少 3 档连续同向增长以排除单档 GC/arena 尖峰，斜率取两两斜率的中位数（Theil-Sen）而不是最小二乘，避免一个离群档位改变类别。

## 3. 复杂度

生成 O(n) 输入、执行 O(T(n))、拟合 O(档位数 × 候选数) = O(13×8)，可忽略。测量本身受单档 10 秒、总 60 秒硬上限约束（方案审核实测：所有成功组的测量都在 12 秒内完成，150 秒只在超时场景被吃满）。单 worker 串行处理，60 人 × 5 题的批量场景约 15 分钟。

## 4. 数据

迁移 pg0007 新增两张表：

- `problem_complexity_profiles`：`problem_version_id` 唯一、`family`、`spec`（JSONB）、`source`、`version_no`。用 `python -m scripts.seed_complexity_profiles` 按题目编号写入，幂等，不覆盖已有行。**种子带自动验收**：生成 `n=256` 的输入喂题库自带的 Python 参考解，崩溃就把该题降级为 `EXISTING_CASES` 并记录原因；已入库的可用 `--revalidate` 重验。
- `complexity_reports`：一次提交一份，`status`、`time_class`/`space_class`、置信度、来源、`static_analysis`、`growth`、`summary`、`limitations`，加 `requested_by`、`attempt_no`、`lease_expires_at`、`finished_at`、`error_message`。

worker 用 `FOR UPDATE SKIP LOCKED` 领取，置 RUNNING 并给 180 秒租约，测量在事务外进行，写回前重验租约。租约过期由 `recover_expired` 置 FAILED 并说明，不自动重跑。

pg0008 补齐约束与历史：`time_class`/`space_class` 有取值枚举 CHECK，`status` 与类别是否为空的一致性有 CHECK（已发布必须有类别，排队中必须为空）；实现版本升级重置时把旧结论归档到 `history` JSONB 数组，教师能看出结论被改过。

## 6. 已声明的限制

报告里必须出现、前端必须显示：

- 输入由平台按伸缩档合成，覆盖常见规模，不代表最坏情况或全部合法输入。
- 静态分析依据代码结构，等价改写可能改变结论。
- 结构化语言没有语法树，结论是词法上界。
- 总时间与纯读取同阶时，实测只能给出上界（会明确写）。
- 超时或失败的档位被剔除，并写剔除了几档。
- 有效档位少于 5 时，拟合容易受常数开销影响，置信度不会是 MEDIUM 以上。
- 只差一个 log 因子的两类由结构裁定，结构若看不出该因子，报告会写清分歧。
- 结构裁定要求结构分析本身不是 LOW：C/C++/Java 只有词法分析，此时按实测报并写明分歧（否则会把高置信实测压成低置信结构结论）。
- 无纯读取基线时（C/C++/Java）实测未经输入开销校验。
- 字面量边界只有 `for` 与推导式被识别为常数层；带条件变量的 `while` 一律按输入相关处理，可能把常数 `while` 判高一阶。
- 输入规模固定的题（伸缩档族 `FIXED`）只给结构结论，并明确写出“复杂度描述的是这个固定输入下的代价，不随 n 变化”。
- 复杂度分析不参与评分，不改变评测结果。

## 7. 边界

- 只分析已真实通过的提交；未通过、模拟结果、跨执行环境的结果一律拒绝并给出 409 原因。
- 没有伸缩档的题只出结构结论（`STATIC_ONLY`），不假装测量过。
- 输出规模本身就很大的题（汉诺塔、全排列、数独、格雷码等）标记为不可测量，避免测到输出格式化而不是算法。
- 同报告不随刷新重新随机：一切来自已保存的 JSONB。
